Extraction findings

EZBIND has an eight-byte magic, a member count and an alignment field,
followed by 16-byte records: relative filename offset, stored length,
relative payload offset and filename hash. Alignment values 4 and 64
occur. All discovered .mlb members are in alignment-4 containers.
Custom compressed message members begin 1F 8B 09 00, followed by their
unpacked length and a raw DEFLATE stream. Decoded sizes are checked.

MLT has a section count in byte 3 and absolute section offsets. Ordinary
sections contain a record count and absolute string pointers. Player text
is UTF-16LE; voice cue tables contain ASCII filenames. Some pointers alias
strings in other sections, so section-local bounds are insufficient.
Subtitle sections marked 0x1111 prefix their pointer arrays with 16-bit
frame positions, padded to four-byte alignment with FFFF when necessary.

Every local source record has a stable archive/member/section/index ID,
its decoded offset, and a SHA-256 hash of the original string. Original
text is in work/source/corpus.json and the ignored bilingual batch.

Validation and game integration

Read-only checks passed for source hashes, unique row IDs, the consecutive
80-row dialogue slice, exact control/placeholder order, line-break counts,
glossary names, Japanese residue outside engine controls, and equivalence
between bilingual data and the source-free English export.

These checks do not prove visual fit. The historical initial batch had 202 of
207 records with an English UTF-16 payload longer than the Japanese.
Expanded strings must be relocated and all affected pointers rebuilt;
do not trim the translation to the old byte slots. Font support, wrapping,
archive repacking and native code-path execution are now verified as
described in docs/native-vwf.txt. Real PSP behavior and visual layout
remain untested.
